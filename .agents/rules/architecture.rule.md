# 아키텍처 제약 및 의존성 규칙 (Architecture Rule)

에이전트는 이 프로젝트 내에서 코드를 수정하거나 새로운 모듈을 추가할 때, 시스템의 계층적 무결성을 유지하기 위해 다음 아키텍처 규칙을 반드시 준수해야 합니다.

## 1. 레이어 간 의존성 방향 (의존성 역전 원칙)
이 프로젝트는 도메인 중심의 계층형 아키텍처(또는 클린 아키텍처)를 따릅니다. 의존성은 언제나 **고수준의 비즈니스 로직(도메인) 방향으로만** 흘러야 하며, 인프라스트럭처나 외부 상세 구현을 향해서는 안 됩니다.

* **도메인 레이어 (Domain Layer)**: 
  * 비즈니스 핵심 규칙과 도메인 모델, 리포지토리 인터페이스(추상화)를 포함합니다.
  * **절대 규칙**: 도메인 레이어 내부의 코드에서 외부 인프라스트럭처 레이어(데이터베이스 구현체, 외부 API 클라이언트, 프레임워크 전역 모듈 등)를 직접 참조(Import)하는 행위를 엄격히 금지합니다.
* **인프라스트럭처 레이어 (Infrastructure Layer)**:
  * 도메인 레이어에서 정의한 인터페이스의 구체적인 구현체(예: SQL 데이터베이스 연결, 외부 서드파티 통신 클라이언트 등)를 작성합니다.
  * 인프라스트럭처 레이어는 도메인 레이어를 참조할 수 있습니다.

## 2. 의존성 해결 방식
* 도메인 서비스가 외부 자원(데이터베이스 등)을 사용해야 할 경우, 도메인 레이어 내에 인터페이스(Interface) 또는 추상 클래스(Abstract Class)를 정의하십시오.
* 구체적인 기술 스택(데이터베이스 커넥터, 라이브러리 등)은 인프라스트럭처 레이어에서 해당 인터페이스를 구현(Implement)하도록 조치하고, 런타임에 의존성 주입(Dependency Injection) 메커니즘을 통해 도메인 서비스에 바인딩합니다.

## 3. 위반 사례 검증
* 정적 의존성 검사기(`import-linter` 등)가 설정된 경우, 커밋 전 수행되는 `.agents/skills/run-test/run-test.sh` 단계에서 도메인 계층이 하위/인프라 계층을 임포트했는지 엄격하게 검증합니다. 위반 사례가 적발되면 빌드 및 커밋이 차단되므로 작업 진행 시 모듈 간의 참조 경로를 항상 신중히 검토하십시오.
